This workflow is for theme maintainers working from a Docifly checkout. To create a documentation site that consumes Docifly, start with [Getting started](../getting-started/) instead.

## Preview the living documentation

Install Git and Jigyll 1.13.0 or later. Run these commands from the repository root in a checkout named `docifly`:

```sh
jigyll new .poc/living-docs --theme "$PWD"
cp -R docs/site/. .poc/living-docs/
rm .poc/living-docs/404.html
jigyll serve --source .poc/living-docs --host 127.0.0.1 --port 4322
```

Open <http://127.0.0.1:4322/>. The first command is a one-time installation into a new target. It clones the committed theme through Jigyll's normal installer. The copy transfers only ordinary consumer Markdown, configuration, and content artwork—never layouts, includes, or theme assets. No custom runner or consumer preprocessing is involved.

The installer names the theme after the source checkout. If your checkout is not named `docifly`, change `theme` in the copied consumer configuration to the name generated by the installer. Do not rename the tracked documentation configuration for a local preview.

## Edit and rebuild

`docs/site/` is the maintained source. `.poc/living-docs/` is a disposable installed consumer, not a second authoring location. After editing source pages, copy them again and build:

```sh
cp -R docs/site/. .poc/living-docs/
jigyll build --source .poc/living-docs
```

If the preview server is running, it watches the consumer files. Copying does not remove files: when a page is renamed or deleted, remove its obsolete copy from the disposable consumer too. The generated site is `.poc/living-docs/_site/`.

The installed theme is a Git snapshot, not a live link to uncommitted theme edits. After committing theme changes, update the installed checkout and restart the preview:

```sh
git -C .poc/living-docs/_theme/docifly pull --ff-only
```

Use the actual installed theme directory if your checkout has a different name. Inspect theme changes through this installed consumer rather than copying internal files into the site.

## Read or inspect

Start at the overview, then follow the guides for configuration, navigation, headings, Markdown, code, color modes, deployment, and internals. The [manual-inspection guide](../inspection/) suggests interactions to try; it is not an automated test matrix. For automated coverage, use the [maintainer browser acceptance gate](../internals/#maintainer-browser-acceptance); its screenshots are failure diagnostics, not visual-parity baselines.

The documentation is a separate consumer: running `jigyll build` at the repository root is not the documentation build. The former root welcome scaffold has been replaced by the documentation overview.

The historical POC notes remain in `docs/poc.md`. Their evidence is retained as history, not as a claim that the current site has complete visual parity or interaction parity with stock Starlight.
